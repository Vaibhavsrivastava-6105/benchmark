# Implementation Plan - LLM Benchmark Lab (Phase 2)

This plan outlines the next phase of LLM Benchmark Lab, moving from the core benchmarking framework to enterprise-grade production utilities.

---

## 1. Scope of Phase 2

### 1.1 PostgreSQL Database Support (Production Profile)
* **Objective**: Allow the backend to dynamically switch between SQLite and PostgreSQL based on `DATABASE_URL`.
* **Details**: Integrate Alembic for database schema migrations. Update `database.py` connection pooling to handle PostgreSQL connections efficiently.

### 1.2 Interactive Model Downloader
* **Objective**: Import and download models via the Web UI without manual terminal actions.
* **Details**:
  * **Ollama**: Expose backend endpoint calling the Ollama local pull API (`/api/pull`) to track download progress in real-time.
  * **Hugging Face Hub**: Use `huggingface_hub` client library to download weights on background worker threads.
  * **GGUF Imports**: Allow registering local paths to `.gguf` files.

### 1.3 Secure Docker Code Execution Sandbox
* **Objective**: Evaluate programming responses by executing output scripts inside isolated Docker containers rather than simple syntax checks.
* **Details**:
  * Write a sandboxing script that spawns a lightweight, resource-constrained Python container (e.g., `python:3.11-slim`).
  * Pipe the model's generated code, execute unit tests, capture stdout/stderr, and enforce a 5-second execution timeout.

### 1.4 Semantic Similarity Evaluator
* **Objective**: Measure free-form response accuracy against expected answers using vector embeddings.
* **Details**: Add a `semantic_similarity` evaluator type in `evaluator.py`. Utilize `sentence-transformers` (e.g., `all-MiniLM-L6-v2`) locally to compute cosine similarity scores.

### 1.5 Standalone HTML/PDF Report Exports
* **Objective**: Generate fully styled, offline-ready reports with embedded charts and matrices.
* **Details**: Implement backend export routes using Jinja2 templates (HTML) and compile to PDF or self-contained HTML reports featuring charts rendered as SVG vector elements.

### 1.6 Concurrency Saturation Curve & Threshold Graphing
* **Objective**: Automate capacity planning by identifying where server throughput peaks and latency degrades.
* **Details**:
  * Run a multi-concurrency stress suite (e.g., concurrency 1, 2, 4, 8, 16, 32).
  * Calculate the **Maximum Efficient Concurrency** (peak aggregate tok/s) and **Saturation Point** (where p95 latency exceeds 2x baseline).
  * Display a throughput vs. concurrency graph on the comparison page.
